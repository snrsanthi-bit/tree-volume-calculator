# Tree Calculation

# 1. サービス概要

TreeCalculationは、林業現場で行う材積・地積の計算から、作業地点や計算履歴の記録までを一元管理する林業現場向けWebアプリです。

林業現場作業員が「その場で計算できる」だけでなく、「どこで、どれだけ作業したか」を後から確認できるようにすることで、現場での計算・記録作業の負担を減らします。

# 2. このアイデアはどこから生まれたか

## 2-1. きっかけとなった体験・感情

林業をしている友人から、「社員が材積の計算をうまくできない」「アプリでどんなことができるかわからない」という話を聞いたことがきっかけです。

林業現場では、材積の計算に電卓や材積表を使用することがあります。そこで、スマートフォンから必要な数値を入力するだけで簡単に計算できるものがあれば、現場で便利なのではないかと考えました。

最初は材積計算だけを行う簡易的なアプリとして作り始め、その後、地積計算なども追加しました。

現在は、単に計算するだけではなく、実際の林業現場で「どこで作業したのか」「どれだけの材積を扱ったのか」といった情報まで残せるサービスに発展させたいと考えています。

## 2-2. なぜそれが「気になった」のか

自分自身が林業従事者ではないからこそ、身近な人から聞いた「計算がうまくできない」「アプリで何ができるかわからない」という話が気になりました。

もともと、身の回りの不便や「これ、もっと簡単にできないのか？」ということを気にすることが多く、実際に動くものを作りながら仕組みを理解することにも興味があります。

今回も、林業という自分にとって馴染みの薄い分野だからこそ、「実際の現場では何が不便なのか」を知りながら、アプリで解決できることを考えていきたいと思いました。

# 3. 課題の整理

## 3-1. 表に見えている困りごと

最初に見えていた困りごとは、

「材積を計算するのが難しい・手間がかかる」

ということです。

そのため、まずは直径と高さを入力するだけで材積を計算できる機能を作りました。現在の実装でも、直径・高さから材積を計算する機能と、三角形の辺から地積を計算する機能を実装しています。

## 3-2. 本当に解決したい課題

### なぜ？

材積の計算に時間がかかったり、計算方法が分からなかったりすると、現場での作業を止めてしまうから。

### なぜ？

計算そのものだけではなく、計算した結果を後から確認したり、どの現場の結果なのか整理したりする必要があるから。

### なぜ？

現場で発生した情報がその場限りの計算結果になってしまうと、作業実績として活用しにくく、後から記録・集計する作業が別途必要になるから。

### 本当に解決したい課題

**林業現場で発生する「計算」と「記録」を別々に行うことで生じる手間を減らし、現場で発生した情報をそのまま業務記録として残せるようにすること。**

# 4. 想定ユーザーについて

## 4-1. 想定しているユーザー

### 年齢

20〜30代程度の林業現場作業員。

### 理由

スマートフォンを日常的に利用しており、紙や電卓だけでなく、スマートフォンを使った業務にも抵抗が少ない層を最初のユーザーとして想定しています。

### 生活・状況

森林内で伐採・測量などの作業を行っており、作業中に材積や面積を確認したり、その結果を記録したりする必要がある人。

### 理由

現場で計算する必要があるタイミングに、その場でスマートフォンから計算・記録できるようにします。

### 環境

スマートフォンを持って森林内などの屋外で作業する環境。

### 理由

屋外ではPCを広げて入力することが難しいため、スマートフォンから短時間で操作できるUIを目指します。

また、将来的には通信環境が不安定な森林内でも利用できるよう、計算など一部機能のオフライン利用も検討します。

## 4-2. 自分とユーザーの距離

**身近な誰か**

林業をしている友人から実際に困りごとを聞いたことが、このサービスを作る直接のきっかけになっています。

そのため、自分自身の課題ではありませんが、実際の利用者から話を聞きながら改善できる距離にあることが強みだと考えています。

## 4-3. 実際に使われる可能性について

最初に使ってもらいたいのは、きっかけとなった友人や、その周囲の林業現場作業員です。

現場で材積や地積を計算する場面で、「電卓や紙の代わりに使う」という形から利用を始めてもらうことを想定しています。

現在の代替手段は、電卓や材積表などです。READMEでも、現場では電卓や材積表を使うことが多いとしています。

そのため、単純な計算機能だけでは既存の手段を置き換える理由が弱いと考えています。

そこで、計算結果を保存し、現場・作業地点・日付などと紐付けることで、「計算するためだけのアプリ」から「現場の記録を残すためのアプリ」にすることを目指します。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ

最初は、現場で材積や地積を計算したいときにサービスを知り、スマートフォンからそのまま利用します。

最初の利用では、複雑な設定を必要とせず、計算機能だけでも利用できるようにします。

その後、計算結果の保存や作業地点の登録などを利用することで、「前回の計算を確認したい」「今日の作業実績を確認したい」といった場面でも使うようになることを想定しています。

将来的に会社単位で利用する場合は、会社・組合ごとにアカウントを管理し、管理者と作業者で利用できる機能を分けることも検討しています。

# 5. 既存サービス・競合調査

## 5-1. 似たサービスの調査

### サービス名

Timberlog 材積計算

### URL

[App Store - Timberlog 材積計算](https://apps.apple.com/jp/app/timberlog-%E6%9D%90%E7%A9%8D%E8%A8%88%E7%AE%97/id1667253703?platform=ipad&utm_source=chatgpt.com)

### どんなことができるか

丸太の直径・長さから材積を計算できるほか、複数の検量方法、樹種・品質の記録、リスト管理、Excel・PDF出力などに対応しています。

また、完全オフラインで利用できることも特徴として挙げられています。

他にも、林業向けのGIS・測量サービスでは、地図上での面積計測、材積・樹高曲線の解析、位置情報共有などを提供しているサービスがあります。

## 5-2. それでも自分が作りたい理由

既存サービスを調査したところ、材積計算や森林GIS、生産管理など、それぞれに特化したサービスが存在していました。一方で、きっかけとなった林業従事者からは「既存のアプリは使いにくい」という声を聞いていました。

そこで、既存サービスの機能を単純に増やすのではなく、実際に使用する人に試してもらい、意見を聞きながら現場に必要な機能や操作方法を考えていくことにしました。

「作り手が考えた林業アプリ」ではなく、「実際の現場の声を取り入れながら育てる林業アプリ」にすることが、このサービスを作りたい理由です。

## 5-3. 差別化を「体験価値」で表現する

**林業現場の作業員が、実際の作業の中で感じる「使いにくい」「こうだったら便利」を反映しながら、現場に合った計算・記録環境を作っていくアプリ。**

単に材積や面積を計算するのではなく、

「計算する」
↓
「現場と紐付ける」
↓
「記録として残る」
↓
「後から確認できる」

という一連の体験を提供することを目指します。

# 8. このアプリの懸念点とその対策

## 懸念点①

### 何が問題になりそうか

既存の材積計算アプリや林業向けGISサービスが存在するため、単純な計算機能だけでは利用する理由が弱い可能性があります。

### なぜそう思うか

実際に、材積計算だけでなく、複数の検量方法、履歴管理、Excel・PDF出力、オフライン利用まで対応したサービスがすでに存在しています。

また、林業向けGISでは、面積計測や位置情報共有、材積解析など、より高度な機能を持つサービスも存在します。

### そのために考えている対策

最初から既存サービスと機能数で競争するのではなく、実際の利用者に使ってもらい、現場で何が必要なのかを確認しながら改善します。

特に、「計算」だけで終わらず、「計算結果を現場・作業・日付と紐付けて記録する」という方向に発展させることで、現場の業務フローに組み込めるサービスを目指します。

### UI・体験の改善

林業現場ではスマートフォンを持って屋外で利用することを想定しているため、入力項目を減らし、片手でも短時間で操作できるUIを目指します。

また、現場では通信環境が安定しない可能性があるため、最終的には計算などの基本機能をオフラインでも利用できる構成を検討します。

「作る → 実際に使ってもらう → 意見を聞く → 改善する」というサイクルを繰り返し、現場で本当に使われるサービスにしていきます。

# 10. 技術スタック

## 10-2. 技術選定の比較検討

| 候補              | 採用/不採用 | 理由                                                       |
| --------------- | ------ | -------------------------------------------------------- |
| Ruby on Rails   | 採用     | これまで学習・開発してきた技術であり、短期間でサービスを完成させやすい                      |
| React / Next.js | 今回は不採用 | 興味はあるが、キャッチアップによって本リリースまでの開発期間が伸びる可能性があるため               |
| Vue.js          | 不採用    | 今回のサービスではRails + Hotwireで必要なUIを実現できると判断                  |
| PostgreSQL      | 採用     | Railsとの組み合わせで利用経験があり、業務データの保存にも適している                     |
| Docker          | 採用     | 開発環境を統一し、デプロイ環境との差異を減らすため                                |
| Hotwire / Turbo | 採用     | Railsを中心とした構成を維持しながら、ページ全体を頻繁に再読み込みせずインタラクティブなUIを実現できるため |

### 今回チャレンジしたい点

これまで作ってきた単純な計算アプリから、複数ユーザー・会社単位のデータ管理を行う業務アプリへ発展させることです。

特に、

* 認証・権限管理
* データの関連付け
* マップ情報と業務データの連携
* 履歴・集計
* オフライン利用を見据えた設計

などに挑戦したいと考えています。

### 不安な点

マップAPIや位置情報を扱う部分はこれまで十分に経験していないため、技術調査や実装に想定以上の時間がかかる可能性があります。

また、業務アプリとして利用することを考えると、単純に機能を実装するだけではなく、データの扱いや権限設計についても慎重に考える必要があります。

## 10-3. キャッチアップ不足の懸念

今回のサービスでは、これまで利用してきたRailsを中心に開発することで、キャッチアップにかかる時間を抑え、本リリースまでの完成度を優先します。

一方で、ReactやNext.jsなど、今後学習したい技術もあります。

そのため、Reactについては本リリース後に単体でキャッチアップを行い、実際にアプリへ組み込む技術的な検証をした上で、必要であれば導入する方針とします。

本リリース前に新しい技術を増やしすぎることで、Issueの見積もりや開発期間が不明瞭になることを避け、まずは現在の技術スタックでTreeCalculationを完成させることを優先します。
